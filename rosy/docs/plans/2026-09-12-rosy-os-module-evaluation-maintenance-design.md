## 1. 우리가 만드는 제품
ROSY OS는 Raspberry Pi OS Lite 위에서 동작하는 로봇 런타임 배포판이다. 디바이스에 위치하여 하드웨어와 ROS 실행환경을 관리하고, 웹 운영·제어 API·상태·진단·복구를 제공한다. 커널을 새로 만드는 계획은 아니다.

최종 업무는 다양한 직사각형 박스를 바닥에서 집어 Pinky에 싣고, 운반 후 지정된 바닥·팔레트에 내려 배치·적층하는 것이다. 현재 OMX 모델과 물체 중량은 미정이다. 이 업무를 지원하되 다음 세 층의 책임을 분리한다.

| 층 | 책임 | 평가 단위 |
|---|---|---|
| 호스트·런타임 | 부팅, 식별, 권한, 서비스, 릴리스, 복구 | 장치가 예측 가능한 상태로 준비되고 복구되는가 |
| 공통 로봇 기능 | 하드웨어, ROS, API, 인식, 좌표, 주행, 암, 명령 소유권 | 기능의 준비·오류·중단·관측 계약이 명확한가 |
| 디바이스 작업 애플리케이션 | 집기 순서, 운반·하역, 박스 배치·적층 | 실제 물체의 이동 결과를 확인하고 실패를 복구하는가 |

작업 애플리케이션도 디바이스에서 실행할 수 있다. 그러나 박스 재고·적층 규칙을 OS 코어에 넣지 않는다. Fleet는 선택적인 외부 조정자이며 로컬 제어 루프의 필수 연결로 만들지 않는다.

기존 경계는 [v1 배포 설계](2026-09-01-rosy-os-v1-image-release-design.md)와 [모듈 분리 기준](2026-09-06-module-split-criteria.md)을 따른다. 외부 진입은 rosy_core이며 외부 클라이언트는 ROS에 직접 접속하지 않는다. CORE의 FastAPI와 rclpy는 기존 단일 프로세스 구조를 유지한다. CommandManager는 유일한 cmd_vel 발행자다. 암 관절 명령은 별도 제어 계약이 필요하다. CORE에서 /dev·Docker socket·root/systemd를 직접 조작하지 않는다.

## 2. 구성 선택
전체를 하나의 업무 프로그램으로 묶으면 초기 연결은 빠르지만 하드웨어 교체와 업무 변경이 서로 영향을 준다. 반대로 모든 기능을 독립 서비스로 만들면 배포·통신·복구 비용이 커진다. **기존 런타임 경계를 유지하면서 논리 모듈의 계약과 평가를 분리**하는 안을 권장한다. 아래 14개는 평가 단위이며 패키지·프로세스 14개를 만들라는 지시가 아니다. GPU/NPU는 영상 모듈의 교체 가능한 실행 자원이며 필수 장치로 고정하지 않는다.

## 3. 모듈별 책임과 평가
책임자는 우선 역할로 지정한다. 실제 담당자·대리 담당자가 배정되기 전에는 유지보수 준비 완료로 판정하지 않는다. 현재 구현 근거와 테스트 파일은 [소스 기준선](2026-09-12-rosy-os-module-evidence-baseline.md)에 분리했다.

| ID / 모듈 | 입력 → 결과·책임 | 핵심 평가와 실패 처리 | 유지보수 경계 / 책임 역할 |
|---|---|---|---|
| M01 호스트·식별·전원 | 보드·저장장치·전원 → 식별·부팅·호스트 상태 | 부팅 반복, 식별 보존, 저전압 관측. 불명확한 상태에서 구동 허용 금지 | OS 이미지·네트워크·배선 인벤토리 / 플랫폼 |
| M02 하드웨어 어댑터 | 장치 프로토콜 → 표준 상태·제어 결과 | 장치 오인식·연결 단절·재접속·오류 코드. 재접속만으로 동작 재개 금지 | 모델·펌웨어 호환표, 교체 절차 / 장치 |
| M03 ROS 실행환경 | 모드·노드·토픽 → 기능 준비 상태 | 프로세스 생존과 데이터 최신성 분리, 시작 순서·노드 고장·교착 평가 | catalog·launch·QoS·시간 기준 / 플랫폼 |
| M04 API·인증·capability | 인증된 요청 → 검증된 명령·상태 | 권한 거절, 중복 요청, 미구현 기능 광고 0건. 불가능한 명령은 이유와 함께 거절 | 버전·권한·오류 계약 / CORE |
| M05 영상·OpenCV·추론 | 시각 포함 영상 → 전처리·물체 후보·품질 | 조명·가림·프레임 만료·지연·메모리. 오래된 영상으로 새 집기 금지 | 카메라·전처리·모델·가속기 버전 / 비전 |
| M06 보정·좌표·공간 상태 | 센서·tf·보정 → 공통 좌표와 유효성 | 좌표계·단위·시간·보정 만료, 실측 위치 오차. 유효하지 않으면 조작 보류 | 보정 원본·치구·버전; 업무 재고는 앱 소유 / 로봇 통합 |
| M07 베이스 이동 | 목표·이동 제한 → 도착·정지·실패 | 위치 오차, 실제 정지, 경로 복구, 적재·팔 수납 조건. 안전 경로 있으면 우회 | 맵·기구·속도·정지 조건 / 주행 |
| M08 암·그리퍼 | 집기 자세·물체 조건 → 관절 동작·집기 관측 | 도달·충돌·한계·집기 실패·낙하·접근/후퇴. 완료 응답과 물체 확보를 구분 | OMX별 어댑터·URDF·그리퍼·관절 제한 / 조작 |
| M09 작업 실행 앱 | 주문·관측 → 단계 기록·결과·복구 | 이동→정지→재인식→집기→확인→수납. 취소·재부팅·중복 실행 때 물체 상태 재확인 | 작업 상태·재시도·보상 동작 / 작업 앱 |
| M10 배치·적층 앱 | 박스·적재함·접근 조건 → 실행 가능한 배치 | 간섭·지지·무게중심·접근·후퇴·하역 순서. 해 없으면 이유를 반환 | 박스 제약·계획 알고리즘·시나리오 / 작업 앱 |
| M11 안전·명령 소유권 | 조작자·자동화·장치 상태 → 실행 허가·제한 | 동시 명령·통신 단절·비상 중단·재가동. 실패를 성능 점수로 상쇄 불가 | 공통 중재와 장치별 정지 정책 / 제어·기구 |
| M12 웹 운영·정비 | 작업자 입력·상태 → 조작·진행·복구 안내 | 실제 브라우저 권한, 중복 클릭, 연결 상실, 실패 이유. 접수와 완료 구분 | 기존 정적 웹 기반, 운영/정비 권한 / UI |
| M13 진단·증거 | 로그·상태·버전 → 사건 추적·진단 묶음 | 사건과 명령·관측 연결, 시간 오차, 디스크 부족, 민감정보 제거 | 보존·용량·수집·알람 / 운영 |
| M14 릴리스·복구 | 검증된 bundle·설정 → 활성화·복구 결과 | 손상·호환 불일치·건강 확인 실패·전원 중단. 복구 후 core부터 확인 | 서명·manifest·이전 버전·재인수 / 릴리스 |

ROS lifecycle는 준비·활성·오류 경계를 설계하는 참고 모델이다. 모든 기존 노드가 lifecycle 구현인 것은 아니다. 평가 상태를 새 공개 API enum으로 간주하지 않는다. [ROS 공식 설계](https://design.ros2.org/articles/node_lifecycle.html)

## 4. 평가 프로파일
| 프로파일 | 필수 범위 | 인수할 수 있는 주장 |
|---|---|---|
| P0 Pinky 단독 | M01–04, M07, M11–14; 사용한 센서의 M06 | 선택한 환경에서 베이스 운영·복구 |
| P1 고정 OMX 작업대 | M01–06, M08–09, M11–14; 적층 사용 시 M10 | 고정 작업대의 인식·집기·배치 |
| P2 Pinky 운반 + 고정 OMX | M01–14 | 정해진 정차·인계 조건에서 운반·집기·하역 |
| P3 Pinky 직접 탑재 모바일 암 | M01–14 + 물리 탑재 gate | 탑재·이동·바닥 집기·적층의 결합 결과 |

미사용 기능은 프로파일에서 사전에 제외한 경우만 N/A다. 필수 기능의 미구현·미측정은 HOLD다. P1/P2 성공으로 P3 성공을 대체하지 않는다. 물리 탑재 gate는 질량·하중·무게중심·전원·체결·센서 시야·바닥 도달을 포함한다. 현재 P3는 HOLD이며, 플레이트 크기만으로 불가능하다고 단정하지 않는다.

## 5. 업무 전체 인수 기준
각 단계는 명령 결과와 물체 관측을 함께 기록한다.
1. 박스와 집기 위치를 유효한 좌표·시각으로 확인한다.
2. 베이스 정지와 팔 작업 허가를 확인한 후 집는다.
3. 물체 확보를 확인하고, 싣기 후 지지·팔 수납 상태를 확인한다.
4. 적재 조건 안에서 주행하고 실제 정차 후 재인식한다.
5. 배치의 공간·지지·접근 조건을 확인하여 내려놓고 그리퍼를 후퇴시킨다.
6. 실제 배치와 누락·중복·낙하 여부를 확인하여 작업 기록을 닫는다.

직사각형 형상은 초기 가정이다. 영상이나 깊이만으로 무게를 안다고 간주하지 않는다. 최초 평가는 치수·질량을 실측한 등록 블록으로 제한한다. 불명확한 물체·보정·장면은 사람이 확인하거나 재관측할 수 있어야 한다.

## 6. 유지보수 원칙
- 각 모듈에 주 담당·대리, 계약, 설정 범위, 재현 절차, 고장 탐지, 복구 절차, 재인수 시험을 연결한다.
- 카메라·암·그리퍼·브래킷 변경은 관련 보정과 도달·충돌 검증을 다시 수행한다.
- runtime bundle rollback, 설정/보정 데이터 호환 복구, SD 재이미징, 장치 펌웨어 복구는 별도 절차로 관리한다. v1에 전체 OS A/B 업데이트를 약속하지 않는다.
- 업데이트·재부팅 후 core 건강 확인과 물리 구동 승인을 분리한다. 물체를 잡은 암을 무조건 torque-off하지 않는다. 전원 상실·통신 단절에서 지지·유지·정지할 방법은 선정 기구의 검증 항목이다.
- 운영 화면은 작업 상태와 조치를 보여 주고 상세 버전·로그·오류 분석은 정비 화면에 둔다.

수치 목표·평가 기록·변경 영향은 [평가표와 유지보수 목표](2026-09-12-rosy-os-evaluation-scorecard.md)를 사용한다.


전체 구조와 구현 의존 순서는 [시스템 구조·개발 로드맵](2026-09-12-rosy-os-system-architecture-roadmap.md)을 먼저 읽는다.


## 제품 경계 확정: Control 흡수
사용자 결정에 따라 Rosy Control의 기존 기능·테스트·설정·기동·웹 운영을 Rosy OS 내부로 흡수한다. 별도 Control 제품과의 연결을 최종 구조로 두지 않는다. 흡수 목적지와 A0–A6 이전 순서는 [수정 로드맵](2026-09-12-rosy-os-system-architecture-roadmap.md)을 따른다. OS 내부 모듈 분리는 유지하며 소스 흡수는 2026-09-13 기준 완료되었으며, 런타임 및 Device 게이트는 남아 있다.
