## D-163 신호등 관측은 제어와 분리된 읽기 전용 평면이며, 카메라 역할은 셋으로 나눈다

**Status:** Accepted (2026-09-22). 신호등 모듈의 관측 경계다.

**Context:** 알리 토이 신호등(본체 물리 버튼 1개 · 모드 사이클 · 건전지 교체식)을
관제(Fleet 콘솔)가 제어하는 구조에서 두 맹점이 확인됐다. (S-02) 전기 센서 없이는
"명령했는데 실제로 켜졌는가"를 접점 쪽에서 볼 수 없다. (W9) 제품의 카메라 프롭은
**속도 확인(단속) 컨셉 요소**라 관측용으로 재활용하면 안 된다. 그리고 "카메라"라는
한 단어가 표시 피드·속도 계측·신호 상태 관측을 동시에 가리키면, 화면용 압축·지연이
계측 숫자를 오염시킨다.

**Decision:**

- 관측은 **제어와 분리된 읽기 전용 평면**이다. `signal/observer/` 는
  `GET /observed`(+`/healthz`)만 노출하고 POST·명령 경로 자체가 없다(경계 시험이
  고정). 관측 서버가 제어 권한을 갖는 일은 구조적으로 불가능하다.
- 카메라 역할은 **셋으로 나눈다**: 표시 피드(보여주기) / 속도 계측(숫자) / 신호
  상태 관측(빛의 실측). 한 스트림을 셋이 나눠 쓰게 하지 않는다 — 계측이 필요해지면
  별도 파이프라인을 둔다.
- **속도의 1차 출처는 로봇 오도메트리**(Fleet pose 차분)다. 카메라 속도 계측은
  독립 검증자일 뿐이고, 두 출처가 모일 때만 Fleet 가 과속을 판정한다(독의
  2-소스 원칙 준용).
- 관측 1차 채택은 **F-EXT(외부 카메라)** — 제품을 개조하지 않는다. 카메라 프롭은
  속도 확인 전용(마운트 재활용 금지). F1(내장 TCS34725)·F2(전원 MOSFET)는 벤치
  후 재판정한다.
- 프레임 소스는 추상화한다(cv / file / picamera2) — Windows 벤치와 Pi 현장이 같은
  분류기로 돈다. **Pi 배치 자체는 미결정**이며, 소스 추상화 때문에 나중에 결정해도
  판정 코드가 바뀌지 않는다.
- 색 이름을 필드로 박지 않는다 — 램프는 위치 기반(`left/mid/right/beacon`),
  색은 센서·관측이 **보고**하고, 의미(stop/go)는 운영자의 사이클 지도가 정의한다.
  렌더링 사진과 실물의 색이 달라 보인 사건(초록·청록 논쟁)이 그 근거다.

**Alternatives:**

- 관측을 컨트롤러(ESP32) 안에 넣는 안 — ESP32 로는 OpenCV/YOLO 급 처리가 불가능하고,
  제어 권한과 관측이 같은 프로세스에 있으면 관측 실패가 제어 실패로 읽힌다.
- 제품 카메라 프롭을 관측 센서로 재활용하는 안 — 프롭의 역할(속도 확인 컨셉)을
  훼손하고, 단일 카메라가 표시·계측·관측을 겹임한다.
- 카메라 단독으로 속도를 만드는 안 — 조명·가림·왜곡에 단일 실패점이다.
- v1 에서 YOLO 를 기본 탐지기로 쓰는 안 — 고정 ROI 색 분할로 충분한 문제에 학습
  데이터·모델 관리 비용을 얹는다. 같은 인터페이스 뒤 선택 단계로만 둔다.

**Consequences:** 관측 상시 가동에는 카메라가 필요하다(설치 조건 — 정면, 고정 거리).
"명령 vs 실측"의 갈림이 처음으로 보이므로, Fleet 교차 검증(불일치 → UI faults)이
후속 구현이다. Pi 배치가 확정되면 systemd + picamera2 소스로 같은 코드를 기동한다 —
별도 코드가 없다.

**Validation / Transition:** `signal/observer/test` 14건(합성 프레임 + 명령 경로
부재, 뮤테이션 검증 포함), 계약 시험 `test/test_signal_contract.py` 14건 유지.
벤치는 수용 계획 AC-23(카메라 적합성)·AC-24(Pi 동등성)·AC-25(속도 정확도)로 판정
한다.
