# 0008 — 화물 한 개와 여러 칸의 점유를 분리한다

Status: Accepted, 2026-10-25. 사용자 확인은3×3×3 맵과1×1·2×1·3×1 화물 점유다. Django 유지도 명시적으로 확인했다. 이 결정은 실물 안정성/도달성/현장 수용이 아니다.

기존 칸별 화물 목록은 같은 화물이 여러 칸에 나타나면 중복 ID로 거절한다. 그 검사를 완화해 여러 목록에 같은 ID를 넣으면 수량·이동 횟수가 늘고, 일부 칸만 이동하거나 지지를 잃는 계획이 생길 수 있다. 대신 화물은 배치 하나로 기록하고 전체 점유 영역을 계산한다. [상세 계약](../design/16-multicell-cargo.md).

크기는 기존 Cargo와 분리한 불변 revision으로 보존하며 관측은 해당 화물의 크기 revision·기준 구역/행/열/층·방향을 고정한다. 과거 Cargo에 확인한 크기를 추측해 backfill하지 않는다. 기존 bays 관측/계획과1×1 업무 장부는 유지하고, 새 공간 관측은 별도 schema로 검증한다. 전체 관측 구역, 겹침/범위/전체 지지, 상단 의존 화물과 복귀까지 한 계획으로 대조한다. 임시 장소도 맞는 면적이 있어야 한다. 유효 복귀가 불가능하거나 탐색 한도에 도달하면 부분 이동 없이 HOLD한다.

현재 논리 구현은 화물 높이1격자와 명시한0/90도 방향을 사용한다. 임의 회전·실물 하중/안정성·기하 보정은 추가하지 않는다. 새 공간 계획은 크기/방향/출발·도착 전체에 대응하는 검증된 설치 binding이 없으므로 실행을 차단한다. legacy ARM binding을 재사용해 검증 범위를 확대하지 않는다. 기존 요청/원래 실행/승인/관측 근거 경계는 유지한다.

서버·계정·DB를 함께 바꾸면 데이터 이행과 업무 의미 변경의 원인을 구별하기 어려워진다. 이번에는 Django를 유지하고 공간 모델과 관측 계약을 먼저 바꾼다. FastAPI로의 전환은 이 결정의 구현 범위가 아니다.
