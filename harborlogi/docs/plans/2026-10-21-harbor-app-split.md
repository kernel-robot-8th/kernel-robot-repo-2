# 항만 앱 분할 실행계획

2026-10-21 작성. 2026-10-24 설계 저장소 rosy-docs에서 이전했다(출처: rosy-docs `1b3d80cee73c3bc2d826554fd4f3b06f3d7b1666`의 `가이드/2026-10-21 항만 앱 분할 실행계획.md`). 이전 뒤 정본은 이 문서다. 본문은 작성 당시 기록이며, `rosy-port` 경로는 DL-19에 따라 이 저장소의 `harborlogi/`로 바뀌었다(`rosy-port`는 2026-10-24 은퇴).

> **For agentic workers:** `superpowers:executing-plans`로 한 작업씩 진행한다. 이 문서는 설계 초안이며 새 저장소 생성·외부 게시·실물 동작 지시가 아니다. 공개 계약이 준비된 범위만 연결한다.

**Goal:** 도메인 중립 ROSY 위에서 항만의 회수 순위 변경·매몰 화물 회수 흐름을 구현할 수 있게 업무 모델과 실행·자원 계약을 분리한다.

**Architecture:** 항만 앱은 업무 데이터·정책·화면을 소유하고 ROSY 공개 계약을 어댑터로 소비한다. 암 S/A/B·Pinky·도크·충전 자리는 배치와 허용 후보로 표현하며, 플랫폼의 가용성·admission과 장치 실행 권한을 우회하지 않는다.

**Tech Stack:** Python 3.10 이상, 기존 HTTP/JSON·pytest·YAML/SQLite 패턴을 우선 사용한다. 런타임 플랫폼 Python 패키지·ROS·플랫폼 DB를 직접 의존하지 않는다. 새 SDK·범용 workflow 엔진은 만들지 않는다.

**Spec:** [ADR-0004](../adr/0004-harbor-app-on-domain-neutral-rosy.md)(원래 rosy-docs ADR-07), 최신 문제 정의·UR/SR. 플랫폼 의존 작업은 D-827~829와 rosy-platform `docs/plans/2026-10-21-domain-neutral-application-phases.md`의 W0~W6다.

## 범위·물리 배치·시작 조건

- 암 S 1대는 공급·회수, A/B 2대는 야드 작업이다. Pinky 3대는 공통 운송 풀이고 충전 자리는 한 개로 계획한다.
- 첫 흐름은 회수 시작 전 계획 변경, 방해 화물 처리, 목표 운송·S 하역, 방해 화물 정리·관련 팔 퇴피다. 진행 중 조작의 takeover·공중 인계·동시 강체 파지는 첫 구현 범위가 아니다.
- 자동 도킹·충전 시작은 미확인이다. 초기에는 수동 교대·사용 불가 상태를 다루며 자동 충전은 별도 수용 작업으로 둔다.
- 기존 실물 direct 경로·한 대씩 이동·팔별 단일 명령자·정지·승인·실물 경로 제한을 유지한다. `fleet` 시뮬레이션 성공을 실물 허용으로 기록하지 않는다.
- 구현 경로의 제안은 `Rosy/rosy-port/`(2026-10-24 은퇴, 현재는 이 저장소 `harborlogi/`) 독립 업무 앱이다. 저장소 생성·공개 범위·제품 이름은 H0에서 확인하며, 기존 Vault를 복사한 뒤 이름만 바꾸지 않는다. 아래 파일 목록은 후속 구현안이고 현재 파일이 존재한다는 뜻이 아니다.

## 분할 순서와 완료 기준

| 작업 | 주요 책임 | 의존성 | 개별 완료 산출물 |
|---|---|---|---|
| H0 | 계약·저장소 기준선 | 플랫폼 W0 | 지원 계약표와 앱 생성/공개 범위 결정 |
| H1 | 항만 업무 모델 | H0 | 관측·계획·업무 상태가 분리된 모델과 시험 |
| H2 | 회수 정책 | H1 | 순수 회수 제안과 거절/보류 조건 |
| H3 | 배치·후보 제약 | H1, 플랫폼 W2 설계 | S/A/B·Pinky 풀·충전 한 자리의 검증된 설정 |
| H4 | 공개 계약 어댑터 | 플랫폼 W1·W3, H1 | 접수·근거·완료를 구분하는 HTTP 소비 |
| H5 | 업무 흐름·장부 | H2·H3·H4 | 첫 정상 흐름과 실패·중복·재시작 처리 |
| H6 | 수동 충전 교대 | H3·H4 | 미확인 자동 기능에 기대지 않는 가용성 관리 |
| H7 | 통합·평가 | H5·H6, 플랫폼 W6 | 고정 버전의 시뮬/회귀 결과와 별도 실물 계획 |

H2·H3는 H1 뒤 병행 가능하고 H4는 플랫폼 계약이 준비되는 동안 합성 HTTP 서버로 소비 시험을 작성할 수 있다. H5의 실제 지원 계약 연결은 플랫폼 검토 이후다. 각 작업은 별도 분기·커밋·검토·결과 SHA로 처리한다.

## H0 — 계약 기준선과 앱 준비

**제안 파일:** `rosy-port/README.md`(현재 `harborlogi/README.md`), `pyproject.toml`, `docs/platform-contract.md`.

**입력 → 출력:** 플랫폼 W0의 지원 계약표·ADR-07 → 앱이 사용할 버전·권한·실행 환경·필요 근거와 설치 절차.

- [ ] 저장소·제품명·공개 범위를 확인하고 앱 경로를 확정한다. 비밀값·장치 주소·실제 시리얼은 외부 설정으로 둔다.
- [ ] 운송·팔 작업·조회·근거·정지/취소의 현재 지원 범위와 부족한 계약을 기록한다. 부족한 기능은 플랫폼 변경으로 요청하고 임의 내부 import로 해결하지 않는다.
- [ ] 플랫폼 전체 SHA와 소비 계약 버전을 고정한다. 합성 시험과 실제 고정 서버 통합 시험의 환경을 구분한다.
- [ ] 새 앱의 최소 실행/시험 절차를 확인한다. 업무 기능을 추가하기 전 연결 경계를 검토한다.

**완료:** 실제 배포/장치 활성화 없이 앱의 소유 경로·의존성·지원 계약이 명확하다.

## H1 — 항만 업무 모델

**제안 파일:** `harbor/model.py`, `tests/test_model.py`.

**입력 → 출력:** 컨테이너 ID·슬롯/층·유효한 관측·물리 보유·작업계획 버전·변경 지시 → `YardSnapshot`, `RetrievalRequest`, `PortConstraints`라는 앱 내부 값. 이 이름은 공개 ROSY wire 타입이 아니다.

- [ ] 관측 위치와 예정 위치가 독립이고 오래된 관측·보유 불명이 명시적으로 표현되는 시험을 먼저 쓴다.
- [ ] 컨테이너·슬롯·적층 관계·회수 그룹/순위·변경 지시 버전을 앱 내부 모델로 구현한다. 플랫폼 원장이나 실제 장치 상태를 복제한 별도 정본은 만들지 않는다.
- [ ] 중복 ID·불가능한 적층·없는 화물·버전 불일치를 입력 경계에서 거절한다.
- [ ] 해당 단위 시험 후 모델 변경만 커밋한다.

**완료:** 명령을 보냈다는 이유로 관측 위치·물리 보유가 바뀌지 않는다.

## H2 — 순수 회수 정책

**제안 파일:** `harbor/retrieval.py`, `tests/test_retrieval.py`.

**인터페이스:** `plan_retrieval(snapshot: YardSnapshot, request: RetrievalRequest, constraints: PortConstraints) -> RetrievalProposal`. 결과는 필요한 이동/인계의 제안·제약과 불가 사유이며 실행 권한이 아니다. `RetrievalProposal`은 같은 모듈의 앱 내부 값이다.

- [ ] 목표가 위에 있음, 방해 화물 한 개, 합법 임시 위치 없음, 오래된 관측, 도달 불가 후보의 시험을 먼저 쓴다.
- [ ] 첫 기준선은 허용 위치와 검증된 단일 작업 절차만 사용한다. 임시 위치가 없다고 양팔 보유를 자동 해법으로 선택하지 않고 보류한다.
- [ ] 공정이 지원하는 후보와 입력 제약으로 방해 화물 처리·목표 회수·방해 화물 정리 순서를 만든다. 최적화·AI·플러그인 구조를 선행 도입하지 않는다.
- [ ] 같은 입력의 결정성·실제 실행 부작용 없음·업무 순위 변경 때 플랫폼 수정 없음의 시험을 확인한다.

**완료:** 첫 비교에서 무엇을 제안했는지 설명 가능하고, 가용하지 않은 해결 방식을 성공 계획으로 만들지 않는다.

## H3 — 역할·배치·후보 제약

**제안 파일:** `harbor/site.py`, `config/site.example.yaml`, `tests/test_site.py`.

**입력 → 출력:** 설치 장치·검증된 역할/도달/대기 조건 → S/A/B·운송 풀·도크·충전 자리의 제약. 역할 이름과 실제 identity는 구분한다.

- [ ] 같은 장치의 충돌 역할, 알 수 없는 후보, 충전 자리 수 불일치, 잘못된 목적지/대기 위치를 거절하는 시험을 쓴다.
- [ ] S 한 대·A/B 두 대·Pinky 세 대·충전 한 자리의 예제를 합성 identity로 작성한다. 운송·입고·출고·충전 역할을 Pinky 번호에 하드코딩하지 않는다.
- [ ] A/B 도달·퇴피·공유 구역 제약과 현재 동시 이동 제한을 연결한다. 검증되지 않은 공간이나 능력을 설정 한 줄로 활성화하지 않는다.
- [ ] 예제를 다른 identity로 바꿔도 정책 코드가 바뀌지 않는 시험을 확인한다.

**완료:** 장치 변경은 배치·제약으로 표현하고 플랫폼/장치 검증을 유지한다.

## H4 — 공개 계약 어댑터

**제안 파일:** `harbor/ports.py`, `harbor/adapters/rosy_http.py`, `tests/test_rosy_http.py`. 정확한 요청/응답 필드는 H0와 플랫폼 W1·W3에서 검토한 지원 계약만 사용한다.

**입력 → 출력:** 앱의 작업 제안과 제약 → 공개 API 요청·작업 identity·검증된 상태/근거. 플랫폼 Python 모델을 앱 런타임에 import하지 않는다.

- [ ] 접수만 성공, 유예 응답, 권한 거절, 중복·지연·과거 시도 결과, 관측 만료·재연결의 HTTP 소비 시험을 먼저 쓴다.
- [ ] `move`/`arm` 성공 하나로 물리 보유·퇴피·차량 출발 가능을 추정하지 않는다. 필요한 근거를 조회하거나 명시적 하위 단계로 연결한다.
- [ ] 요청/응답 출처와 task/attempt·계획 버전을 보존하고 플랫폼 DB·ROS·다른 앱 내부 import 없이 소비한다.
- [ ] 합성 서버 계약 시험과 고정 실제 서버 통합 시험을 따로 확인한다. 실제 서버 미실행을 합성 통과로 대신하지 않는다.

**완료:** 업무부는 플랫폼 내부 구조를 모르고, 어댑터는 물리 미확인을 성공으로 바꾸지 않는다.

## H5 — 첫 업무 흐름과 장부

**제안 파일:** `harbor/workflow.py`, `harbor/store.py`, `tests/test_workflow.py`, `tests/test_store.py`.

**입력 → 출력:** 변경 지시·순수 계획·가용성/실행 근거 → 항만 업무 상태와 연결된 작업 기록. 실행 원장은 플랫폼 소유이고 이 저장소는 업무 장부만 소유한다.

- [ ] 같은 지시/버전 재수신은 중복 실행하지 않고, 같은 버전의 다른 내용은 거절하는 시험을 쓴다. 이미 물리 조작 중 새 계획을 받으면 임의로 이어 바꾸지 않고 첫 범위 밖의 상태로 보류한다.
- [ ] H2 제안을 H4 요청으로 연결하고 화물 보유→퇴피→차량 출발 허용→목표 안착→S 하역·방해 화물 정리·팔 퇴피를 해당 근거로 확인한다.
- [ ] 부분 실패·stale 결과·재시작에서 원장과 관측을 대조한다. timeout만으로 화물·슬롯·도크 점유를 풀거나 자동 재시도하지 않는다.
- [ ] 정상·중간 실패·정지·수동 복구 뒤 재관측 흐름을 시험하고 기존 승인/정지 경계를 유지한다.

**완료:** 차량 도착만으로 회수가 끝나지 않고, 최종 완료는 목표 하역과 방해 화물 정리·퇴피까지 포함한다.

## H6 — 수동 충전 교대의 가용성

**제안 파일:** H3의 site 설정, H5의 업무 흐름과 연결되는 `harbor/availability.py`, `tests/test_availability.py`. 장치의 전력·배터리 검증을 이 모듈에서 재구현하지 않는다.

- [ ] 충전 자리 한 개 점유, 대기 차량, 적재 중 요청, 정비·보유 불명 차량의 배정 제외를 시험한다.
- [ ] 초기에는 수동 충전/점검 중임을 운영 상태로 기록하고 작업 배정에서 제외한다. 충전 자리 도착을 충전 시작·완료로 간주하지 않는다.
- [ ] 검증된 플랫폼 에너지 예산이 없는 상태에서 임의 SOC 임계치로 자동 작업 투입을 허용하지 않는다. 자동 도킹·충전 시작·이탈은 지원 계약과 실물 근거가 준비된 별도 후속 변경이다.
- [ ] 차량 한 대가 빠져도 남은 가용 후보로 업무 정책 코드 변경 없이 운용하거나, 안전한 대기로 전환하는 시험을 확인한다.

**완료:** 충전소 한 자리 개념을 반영하되 미검증 자동 기능이 정상 업무의 전제가 되지 않는다.

## H7 — 통합 흐름과 비교 평가

**제안 파일:** `tests/integration/test_retrieval_flow.py`, `docs/validation/<날짜>/result.md`, CI의 전용 통합 job. 실제 저장 위치는 H0에서 확정한 앱 저장소 내부다.

- [ ] 같은 초기 적층·변경 지시·정보 공개 시점·허용 공간에서 기준선과 후속 전략을 비교한다. 준비 비용·목표 S 하역·방해 화물 정리·퇴피까지 시간을 기록한다.
- [ ] 추가 취급·재취급·대기와 S/A/B/Pinky의 병목을 분리해 기록한다. 양팔 사용 장면이나 장비 가동률 자체를 업무 성공으로 대신하지 않는다.
