# Harbor 디자인 철학과 제품 기준

상태: 2026-10-25 제품 디자인 기준안. 사용자 확정은 PC 중심·태블릿 보조·브라우저 웹앱·기존 이미지/테마 유지·**조치 필요 중심의 PC 첫 화면**이다. 아래 원칙과 세부 구조는 이 결정을 실행할 설계안이다. 운영 앱 전체가 구현·수용됐다는 뜻은 아니다.

## 1. 디자인 철학

**현재 업무와 다음 판단이 분명한 관제.**

사용자는 로봇의 모든 수치를 보러 오는 것이 아니라, 맡은 화물이 어디까지 진행됐고 무엇 때문에 멈췄으며 자신이 무엇을 판단해야 하는지 확인하러 온다. Harbor는 그 판단을 돕는 업무 도구다. ROSY의 장치 운영 화면과 연결하되 각 앱의 권한과 근거를 보존한다.

차분한 네이비와 아이보리는 오랫동안 읽는 바탕으로 사용한다. 청록은 선택과 이동을, 오렌지는 주의가 필요한 맥락을 표시한다. 이미지의 컨테이너·협력 로봇은 제품의 정체성을 전달한다. 실제 작업 화면의 중심은 이미지가 아니라 업무와 근거다.

## 2. 원칙이 화면을 바꾸는 방법

| 원칙 | 화면에서 적용할 규칙 | 검토할 조건 |
|---|---|---|
| 다음 판단을 먼저 제시한다 | 작업 제목 아래 현재 업무 상태·막힌 이유·담당 책임·가능한 다음 행동을 묶는다 | 상세를 열고 현재 막힘과 다음 확인을 찾을 수 있다. 알 수 없는 이유/담당을 추정하지 않는다 |
| 업무를 따라 이동한다 | 업무 ID를 목록·계획·실행·근거·기록의 같은 기준으로 사용한다 | 다른 탭으로 이동해도 같은 업무를 보고 있는지 알 수 있다 |
| 필요한 깊이만 연다 | 요약→단계→원본 ID/버전/출처 순서로 정보를 펼친다 | 평소 판단에 소켓·raw JSON·내부 오류를 읽을 필요가 없다. 필요한 검증 ID는 숨겨 없어지지 않는다 |
| 모르는 상태도 명확히 보인다 | 없음·미확인·오래됨·조회 실패·불일치를 구별한다 | 조회 실패 때 ‘0건/정상’, 화면 조회 시각을 원본 관측 시각으로 표시하지 않는다 |
| 판단의 범위를 드러낸다 | Harbor 업무, Fleet 실행, physical receipt, 업무 근거를 각각 이름 붙인다 | receipt 확인을 업무 완료로, 취소 접수를 정지로 표시하지 않는다 |
| 위치와 맥락을 유지한다 | 현재 메뉴·업무·필터·복귀 위치가 일관되게 남는다 | 뒤로 가기 후 검색·필터·선택·스크롤을 복구한다 |
| 색보다 문장을 먼저 읽게 한다 | 상태에는 텍스트와 필요한 이유를 붙인다. 핵심 조작은 명확한 동사로 쓴다 | 색을 보지 못해도 선택·막힘·가능한 행동을 이해한다 |
| 역할에 맞는 작업량을 준다 | PC는 비교·계획·예외 처리, 태블릿은 배정된 대상과 한 번의 현장 확인에 집중한다 | 태블릿에 PC의 밀도와 장비 조작판을 그대로 축소하지 않는다 |

‘빠르게 판단한다’는 사용성 목표다. 아직 실제 운영자 측정 결과나 검증된 처리 시간 수치가 아니다.

## 3. 정보의 우선순위

업무 상세의 읽는 순서는 다음과 같다.

1. **대상:** 업무·화물·현재 단계. 긴 ID는 줄여도 전체 확인과 복사가 가능해야 한다.
2. **판단:** 현재 상태, 막힌 이유, 해결 책임, 다음 확인/행동. 담당이 없으면 ‘담당 미지정’이다.
3. **진행:** 계획된 이동 순서와 현재 단계. 전체 계획 대비 단계 수는 표시할 수 있지만 근거 없는 진행률은 만들지 않는다.
4. **근거:** Fleet job·Action/attempt·receipt와 Harbor 배치·복귀·퇴피 대조.
5. **추적:** 원래 ID·revision·digest·출처·원본 시각·조회 시각·기록.

이 순서는 정보 삭제가 아니라 위계다. 업무 식별과 핵심 상태는 항상 보이고, 긴 digest나 원본 세부 근거는 해당 섹션에서 펼친다. 경고를 모두 붉게 만들거나 매번 modal로 띄워 중요도를 평탄하게 만들지 않는다.

## 4. 브랜드의 역할

| 요소 | 역할 | 사용하지 않을 곳 |
|---|---|---|
| H 아이콘과 Harbor 이름 | 앱 식별, 홈 복귀, favicon | 상태·장비 종류를 대신하는 반복 장식 |
| 네이비 | 전체 앱 탐색, 강한 제목과 구조 | 모든 본문 영역의 어두운 바탕 |
| 청록 | 현재 선택, 링크, 주요 업무 조작 | 의미 없는 ‘정상’ 표시 |
| 오렌지 | 주의·검토 필요 맥락 | 긴급 정지 버튼처럼 보이는 일반 CTA |
| 아이보리/흰색 | 장시간 읽을 작업면과 구분된 표면 | 구분이 안 되는 다수의 떠 있는 카드 |
| 기존 컨셉 배너 | 처음 진입, 제품 소개, 도움말 | 현재 장비 위치·실행 상태 지도나 실물 증거 |

현재 구현은 밝은 작업면과 어두운 헤더를 사용한다. 별도 dark mode·야외 고휘도 테마는 현장 환경과 대비 검증 후 결정한다. 테마 전환 스위치를 먼저 만들지 않는다.

## 5. 인터랙션과 문구

- 한 작업 맥락에서 가장 중요한 행동 한 개를 시각적으로 우선한다. 다른 정당한 행동은 보조 조작으로 둔다.
- 버튼은 결과를 말한다: ‘계획 검토’, ‘현재 상태 다시 조회’, ‘Fleet에서 확인’. 업무가 아직 완료되지 않았는데 ‘완료’를 복귀 버튼으로 쓰지 않는다.
- 운영 쓰기 단계의 ‘제안’, 현장 ‘확인 제출’, Fleet ‘승인’은 구별한다. 현재 로컬 조회 앱에 쓰기 권한이 생겼다고 해석하지 않는다.
- 긴 설명을 작은 회색 글씨로 압축하지 않는다. 핵심 상태와 실패 원인은 본문 크기로 읽게 하고, ID·출처는 보조 위계를 쓴다.
- 애니메이션은 탐색 전환과 피드백에 제한한다. 로봇 이동을 추정한 애니메이션·자동 숫자 증가·깜빡이는 장식은 없다.
- `unknown`은 ‘미확인’, `stale`은 ‘오래된 근거’, `unavailable`은 ‘조회할 수 없음’, `mismatch`는 ‘원래 요청과 불일치’처럼 다음 판단에 도움이 되게 쓴다.

## 6. 현재 화면의 정확한 위치

초기 `a360383`은 실제 장부·Fleet HTTP projection을 읽는 로컬 조회 앱이었고 당시 왼쪽 업무 목록은 전역 네비게이션이 아니었다. [후속 구현](10-navigation-pages-plan.md)에서 전역 메뉴와 업무 목록·탭을 분리하고 조치 필요 운영 현황을 추가했다. 업무 쓰기·인증·현장 사용성은 여전히 별도다.

[DESIGN.md](../../DESIGN.md)와 `.impeccable/design.json`은 구현 화면의 기록이다. [토큰 정본](../../design/tokens.json)을 CSS로 생성해 실제 로컬 페이지가 사용한다. 전체 앱 구조의 미개방 영역은 [네비게이션](08-navigation.md), [토큰·컴포넌트 계약](09-tokens-and-patterns.md)에 구분하며 현재 재고·장비·감사 메뉴가 구현됐다고 표시하지 않는다.

## 7. 다음 구현의 검토 순서

1. 같은 예시 업무로 PC 운영 현황→조치 필요→업무 상세→Fleet 인계→복귀를 보여 준다.
2. 태블릿에서 목록→배정 대상→업무 상세→목록 복귀를 확인한다. 실제 확인 제출은 인증·회차 결속 이후다.
3. 토큰을 CSS로 적용하고 공통 버튼·탭·행·상태·오류 패턴을 먼저 검증한다.
4. 빈 장부·연결 실패·오래된 근거·긴 ID·권한 부족·필터 변경·뒤로 가기를 같은 흐름에서 검증한다.
5. 운영자 검토 후 업무 쓰기를 순차 개방한다. 권한과 API가 없는 메뉴·버튼으로 완성된 것처럼 보이게 하지 않는다.
