# 단계별 구현과 수용 기준

상태: 상세설계안. 아래 순서는 새 구현 제안이며 현재 완료 목록이 아니다. 구현 단계마다 검토된 입력·API 지원·실행 결과를 확인하고 다음 쓰기 기능을 연다. 실제 날짜·인원 배정은 아직 정하지 않았다.

현재 진행: [첫 웹 구현](06-web-integration-plan.md)에서 S1의 작업 목록/상세 시안과 S2의 로컬 조회·실제 ARM HTTP projection을 검증했다. 운영 인증·scope가 없으므로 S2 전체 완료나 이후 쓰기 단계 개방으로 보지 않는다. [검증 기록](../validation/2026-10-25-web-workbench.md)을 따른다.

## 1. 한 단계씩 진행할 순서

| 단계 | 산출물·우선 화면 | 선행 조건 | 완료 증거 / 다음 단계 조건 |
|---|---|---|---|
| S0 제품·계약 검토 | 역할/권한, 사용 환경, 기존/신규 경계, GAP 목록 확정 | 이번 문서 + 현행 팀 UR/SR 대조 | 사람 책임·계정 겸임·개방 범위·미정 항목에 검토 기록 |
| S1 화면 흐름 시안 | PC-04 작업 상세 → PC-03 계획 → PC-01 목록, TB-02 확인 상세 | S0의 핵심 업무와 표현 검토 | 합성 데이터라고 명시한 클릭/시각 시안. 단일/불명/오래됨/근거 부족을 구분. 로봇 API 쓰기 없음 |
| S2 읽기 웹 앱 | 업무 목록·상세·근거·재고와 연결 상태 | framework/배포·인증 경계 선택 | 기존 장부 보존, 순수 GET, 적절한 scope, 실패/접근성/반응형 시험 |
| S3 단일 ARM 제안 | 검토된 계획 고정→현재 단계 제안→원래 key 대조 | GAP-01/02, 검증 binding, simulation 계약 | 1개의 durable intent, 중복/유실/재시작/다중 사용자 거절과 조회 대조 |
| S4 Fleet 승인 인계 | Harbor ID 참조 + Fleet ARM 승인 화면 | GAP-06, 실제 Fleet 로그인·권한 | 사용자 구분·원래 proposal/fence·승인 실패·복귀 후 대조. Harbor 자동 admit 없음 |
| S5 업무 근거·순차 단계 | receipt/Placement/Retreat 대응, confirm/finish, 다음 단계 | GAP-04/05/08 | 인증된 근거·현재 attempt·freshness·복귀/관련 팔 전체 조건 검증. 부족하면 다음 단계 금지 |
| S6 현장 태블릿 확인 | TB-01/02, 회차별 S 퇴피 확인 | GAP-01/03, 실제 현장 식별·신선도 검토 | 다른 회차/차량·만료·중복·오프라인·재시작 후 재사용 거절 |
| S7 이송 연결 | 출발 조건→권한 있는 TRIP 요청→조회 | S6 + GAP-07 | ARM과 다른 접수 의미 확인, 확인 소비/전송 유실의 내구 결속, 자동 재전송 없음 |
| S8 운영 수용 | 현장 관측·binding·권한·복구·감사·사용성 | 앞 단계 및 별도 장치 담당 수용 | simulation/실물 구분, 운영 개방·중지·복구 절차, 보존·백업/복원 증거 |

S3은 단일 이동 simulation부터 시작한다. S5가 끝나기 전에 전체 반출을 자동 진행하지 않는다. S6/S7 미완료를 일반 “출발 확인” 버튼으로 우회하지 않는다. S8 전에는 운영 모드 표시를 켜지 않는다.

## 2. 첫 구현 단위의 구체 범위

첫 화면 작업은 **PC-04 작업 상세**를 권장한다. 업무 상태·Fleet 수행·물리 receipt·업무 근거 부족을 한 화면에서 구분할 수 있는지가 제품의 핵심이다. 정상 예뿐 아니라 `HOLD`, 미관측, 오래됨, 접수 불명, permission denied 시안을 함께 검토한다.

첫 서버 작업은 **읽기 계층과 장부 수명 분리**다. 기존 constructor를 요청별로 실행하지 않고 GET을 순수 조회로 유지한다. 이후에 로그인/권한·감사·업무별 명령 직렬화와 버전 검사를 구현한 뒤 단일 제안을 붙인다. 첫 단계에서 frontend state로 DB를 대신하거나 production token을 브라우저에 저장하지 않는다.

## 3. 수용 시나리오

아래 ID는 제안된 시험 항목이다. 아직 이 시험을 실행하거나 통과한 것은 아니다.

| AC-01 | 관측된 C1 위에 C2, 유효 임시 위치 존재 | 재취급→반출→복귀와 팔/기준 표시. 검토 전 전송 없음 |
| AC-02 | 임시 위치 없음·도달 기준 없음·보유 물체 불명 | 계획 전체 보류. 가능한 일부만 실행하지 않음 |

## 4. 검증 계층과 완료 보고

1. 문서·시안: 역할/상태/현재 API와 신규 제안 구분, source/근거 표기, 실제 사용자가 막힌 이유와 조작 효과를 설명하는지 확인한다.
2. Harbor 단독: 기존 계획·장부 회귀를 유지하고 새 application/read model/권한·동시성 시험을 추가한다.
3. UI: 실제 화면의 PC/태블릿·긴 데이터·키보드·권한·offline 상태를 실행해 확인한다. screenshot만으로 명령/인증/장부 수용을 주장하지 않는다.
4. 고정 양 끝 HTTP: 실제 Fleet simulation, 별도 승인/관측자와 소비자 프로세스로 확인한다. source SHA·fixture·exit·skip·한계를 기록한다.
5. 장치/현장: 별도 장치 담당 수용 계획으로 실제 관측 진위·보정·장치 안전·회차·정지·복구를 검증한다.

기존91tests와 이전 HTTP 통과를 새 웹 UI 수용 결과로 재사용하지 않는다. 플랫폼 pytest는 해당 저장소의 공식 원격 절차를 따르고, 실제 장치 동작·운영 배포·push는 별도 범위를 따른다. UI의 평상시 상태, 오류, 보류, 복구 후 읽기 대조를 각각 확인해야 완료다.

## 5. 구현 전 검토 체크리스트

- [ ] 현행 팀 UR/SR와 이번 초안 ID의 대응을 검토했다.
- [ ] 실제 사람/계정·겸임·업무 scope와 승인 독립성의 의미를 정했다.
- [ ] framework·배포·인증 stack과 브라우저/서버 비밀 경계를 정했다.
- [ ] PC-04/03 및 TB-02의 정상·실패·근거 부족 시안을 검토했다.
- [ ] GAP-01~09 중 해당 구현 단계의 차단 항목을 해소했다.
- [ ] 새 데이터와 기존 장부의 migration·재시작·롤백 조건을 정했다.
- [ ] synthetic/simulation/운영 관측과 실제 수용 범위를 분리했다.

이 체크리스트는 지금 승인된 것으로 체크하지 않는다. 구현 작업을 시작할 때 해당 단계의 구체 파일·계약·시험과 함께 닫는다.
